# RuConnect

**RuConnect** — бесплатный open-source сервер управления для [RustDesk](https://github.com/rustdesk/rustdesk).
Это один Docker-контейнер со своими совместимыми с RustDesk **ID- и relay-серверами** (они заменяют штатные
`hbbs`/`hbbr`), клиентским API и веб-панелью. Развернуть можно где угодно: у себя, в облаке или полностью
без интернета.

**Клиент RustDesk остаётся штатным, без модификаций.** RuConnect реализует HTTP API, на котором клиент
уже общается с RustDesk Server Pro. Благодаря этому бесплатно работают функции, которые обычно платные:

- **учётные записи** в клиенте: вход (с двухфакторной TOTP), личные и общие **адресные книги** с тегами и
  правами по пользователям, вкладка «Доступные устройства»;
- **учёт устройств**: онлайн-статус, ОС/CPU/RAM, владелец, группы устройств, удалённое отключение сессий;
- **аудит**: журнал подключений (кто, откуда, как авторизован, длительность, заметки), передача файлов,
  тревоги безопасности;
- **массовое развёртывание**: `rustdesk --assign` / `rustdesk --deploy` и опции клиента `preset-*`;
- **единый вход**: OIDC-провайдеры (Keycloak, Authentik, Яндекс ID, Google) и LDAP / Active Directory;
- **стратегии**: политики настроек клиента, которые сервер рассылает на устройства (на устройство, группу
  или для всех);
- **группы пользователей** с доступом к группам устройств;
- **организации**: один сервер обслуживает много компаний или филиалов, у каждой свои домены,
  администраторы, пользователи и устройства, полностью изолированные друг от друга;
- **мультисерверность**: один RuConnect обслуживает несколько площадок с ID-серверами, и любой клиент
  подключается к устройствам на всех площадках;
- **встроенные ID- и relay-серверы**, совместимые со штатными клиентами, в том числе с клиентами, вошедшими
  в учётную запись (см. [ниже](#встроенные-id--и-relay-серверы));
- **веб-панель** для всего перечисленного (английский и русский).

## Быстрый старт

Нужны Docker с плагином Compose и открытые для клиентов порты 21114-21117 (21114/tcp, 21115/tcp,
21116/tcp+udp, 21117/tcp).

```bash
git clone https://github.com/BorisGB2001/RuConnect.git ruconnect && cd ruconnect/deploy
cp .env.example .env        # укажите в RUCONNECT_ID_SERVER публичный адрес этого сервера
docker compose up -d
docker compose logs ruconnect | grep password   # сгенерированный пароль admin (только при первом запуске)
docker compose logs ruconnect | grep key=       # Key сервера для клиентов
```

Панель доступна по адресу `http://<хост>:21114`, логин `admin`.

В каждом клиенте RustDesk откройте **Настройки → Сеть → ID/Relay сервер** и заполните поля:

| Поле | Значение |
|---|---|
| ID-сервер | `<хост>` |
| Relay-сервер | `<хост>` (необязательно) |
| API-сервер | `http://<хост>:21114` |
| Key | публичный ключ сервера (его показывает панель и строка журнала `ID server started`) |

После этого войдите в клиенте под пользователем, созданным в панели.

## Встроенные ID- и relay-серверы

В RuConnect есть собственные ID-сервер (rendezvous) и relay-сервер, штатные контейнеры `hbbs`/`hbbr` больше
не нужны. Причина: клиент RustDesk 1.5, вошедший в учётную запись на API-сервере, выполняет с ID-сервером
обмен ключами для защищённого TCP. Штатный `hbbs` 1.1.16 на него не отвечает, и такие клиенты получали
ошибку `Failed to secure tcp: deadline has elapsed`. ID-сервер RuConnect реализует этот обмен (версию 0 и
новую версию 1 с отдельными ключами для каждого направления) и совместим со штатными клиентами, которые им
не пользуются.

- **Key:** ключ сервера хранится в формате hbbs в томе данных (`/data/id_ed25519`, рядом `.pub`). При первом
  запуске импортируется существующий ключ hbbs, смонтированный в `/hbbs` (compose-файл монтирует туда
  `deploy/data`), поэтому клиенты сохраняют настроенный Key; иначе создаётся новый ключ. Клиенты должны
  использовать именно этот Key: запросы подключения с другим ключом отклоняются.
- **Сквозное шифрование:** ID-сервер подписывает публичный ключ каждого устройства ключом сервера, поэтому
  подключающийся клиент может проверить устройство, и сеанс шифруется из конца в конец.
- **ID привязан к машине** (uuid), которая зарегистрировала его первой. Привязка хранится в базе данных;
  регистрация того же ID с другой машины отклоняется. Число регистраций с одного IP ограничено.
- Онлайн-статус (`21115`), регистрация по UDP и TCP, пробивка NAT, подключения в локальной сети и связывание
  через relay работают так же, как со штатными `hbbs`/`hbbr`. `RUCONNECT_ALWAYS_RELAY=true` направляет все
  сеансы через relay.
- **Не реализовано:** WebSocket-порты 21118/21119, поэтому веб-клиент RustDesk не поддерживается.

Чтобы и дальше использовать внешние `hbbs`/`hbbr`, задайте `RUCONNECT_RENDEZVOUS=false` и укажите в
`RUCONNECT_KEY_FILE` путь к их `id_ed25519.pub`. Со штатным `hbbs` 1.1.16 вошедшие в учётную запись клиенты
RustDesk 1.5 снова столкнутся с описанной выше проблемой, а проверка организации при подключении (см. ниже)
работать не будет.

## Организации

Один сервер может обслуживать много организаций (компаний, филиалов). У каждой организации:

- свои **домены** (любое количество имён, все указывают на один сервер и используют один Key);
- свои администраторы, сотрудники поддержки, аудиторы и пользователи;
- свои устройства, группы устройств, группы пользователей, стратегии (со своей стратегией по умолчанию),
  общие адресные книги, токены развёртывания и журналы аудита.

Сотрудники организации видят в панели только её; записи других организаций отвечают `404`, как будто их
нет. **Сотрудники сервера** (пользователи без организации) видят всё, а **администраторы сервера** управляют
организациями, площадками (**Серверы**) и провайдерами входа и переносят пользователей и устройства между
организациями. Названия групп, стратегий и общих адресных книг уникальны в пределах организации; имена
пользователей уникальны на всём сервере.

Принадлежность определяется доменом, через который работает клиент (заголовок `Host` его API-запросов):

- устройство попадает в организацию, на домен которой оно впервые отчиталось;
- пользователи входят только через домены своей организации (или через домен, не принадлежащий ни одной
  организации); учётные записи LDAP и OIDC, созданные на домене организации, попадают в неё;
- клиент, вошедший как участник организации, может подключаться только к устройствам этой организации.
  Это проверяет встроенный ID-сервер. Клиенты без входа и сотрудники сервера не ограничены.

Настройки клиента для организации:

| Поле | Значение |
|---|---|
| ID-сервер | `<домен организации>` |
| API-сервер | `https://<домен организации>` (или `http://<домен организации>:21114`) |
| Key | публичный ключ сервера |

С профилем HTTPS Caddy автоматически получает сертификаты для доменов организаций (см.
[docs/DEPLOYMENT.md](docs/DEPLOYMENT.md#https-recommended)).

## Мультисерверность

В клиенте указывается только один ID-сервер. Однако клиент умеет подключаться к устройству через другой
сервер, если его ID записан в формате `ID@хост:порт?key=<ключ>`. RuConnect использует это так:

1. В панели в разделе **Серверы** добавьте каждую площадку с ID-сервером: адрес и публичный ключ. На
   площадке филиала работает `ruconnect id-server` (только ID- и relay-серверы) или штатные `hbbs`/`hbbr`.
2. Клиенты площадки указывают API-адрес своей площадки: `http://<ruconnect>:21114/s/<slug>`.
   Для площадки по умолчанию адрес остаётся обычным.
3. RuConnect знает, на какой площадке каждое устройство. В адресных книгах и во вкладке «Доступные
   устройства» он выдаёт устройства *других* площадок в виде `ID@хост?key=...`. Пользователь нажимает
   «Подключиться», и клиент сам идёт через нужный сервер.

Устройство одновременно зарегистрировано только на одном ID-сервере. Подключаться с клиента можно к
устройствам всех площадок.

## Единый вход

**OIDC**: добавьте провайдера в панели (**Провайдеры входа**) и зарегистрируйте у него адрес
перенаправления, который показывает панель (`https://<хост>/api/oidc/callback`). После этого в клиенте
появится кнопка входа через провайдера. Пользователи сопоставляются по подтверждённому email. Если включить
автосоздание, учётная запись создастся при первом входе.

**LDAP / Active Directory**: задайте переменные `RUCONNECT_LDAP_*` (см. `.env.example`). Участники группы
`RUCONNECT_LDAP_ADMIN_GROUP` становятся администраторами, а `RUCONNECT_LDAP_REQUIRED_GROUP` ограничивает
круг тех, кто может войти. Локальная учётная запись с паролем никогда не перехватывается записью каталога
с тем же именем.

## Стратегии

Стратегия — именованный набор опций клиента, например `enable-file-transfer=N` или `approve-mode=click`.
RuConnect рассылает её устройствам через heartbeat. Сначала действует стратегия самого устройства, затем
стратегия его группы, затем стратегия по умолчанию (его организации). Пустое значение возвращает опцию к значению по умолчанию.

## Массовое развёртывание

В панели (**Обзор → Настройка клиента**) для каждого сервера генерируется строка конфигурации. Её вставляют
в клиенте в **Настройки → Сеть → ID/Relay сервер → Импорт** или применяют командой
`rustdesk --config <строка>` (от администратора). Чтобы назначить устройства пользователям и группам,
используйте токен развёртывания из **Настроек**:

```bash
rustdesk --assign --token <ТОКЕН> --user_name alice --device_group_name Office
```

Подробнее см. [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).

## Настройка

Все параметры задаются переменными окружения, полный список приведён в [README.md](README.md#configuration)
и [`deploy/.env.example`](deploy/.env.example).

Основные переменные встроенных серверов: `RUCONNECT_RENDEZVOUS` и `RUCONNECT_RELAY` (включены по умолчанию),
`RUCONNECT_RENDEZVOUS_PORT` (21116, порт ниже него, 21115/tcp, обслуживает NAT-тест и онлайн-статус),
`RUCONNECT_RELAY_PORT` (21117), `RUCONNECT_RELAY_SERVER` / `RUCONNECT_RELAY_SERVERS` (relay, выдаваемый
клиентам; по умолчанию хост ID-сервера с портом 21117), `RUCONNECT_ALWAYS_RELAY`,
`RUCONNECT_PRIVATE_KEY_FILE` (`/data/id_ed25519`), `RUCONNECT_IMPORT_KEY_FILE` (`/hbbs/id_ed25519`).
`RUCONNECT_KEY_FILE` нужен только для внешнего hbbs.

**HTTPS.** В compose-файле есть необязательный фронтенд Caddy (`docker compose --profile https up -d`) с
автоматическими сертификатами Let's Encrypt, см. [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md#https-recommended).
С любым другим обратным прокси отдавайте порт 21114 на **443**, потому что клиент превращает
`https://host:21114` в `https://host`. Самоподписанные сертификаты тоже работают.

**Сброс пароля администратора:** `docker compose exec ruconnect ruconnect passwd admin '<новый пароль>'`.

**Резервная копия:** всё состояние, включая ключ сервера, хранится в volume `ruconnect-data`
(`/data/ruconnect.db`, `/data/id_ed25519`).
